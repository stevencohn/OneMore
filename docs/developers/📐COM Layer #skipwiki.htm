What is the COM Layer?

 

The OneMore add-in never talks directly to OneNote. All commands must go through a small connection layer. This layer has two main parts:

 

  1. ApplicationFactory - Creates and activates the OneNote connection
  2. OneNote wrapper - Sends commands and handles problems

 

This design exists because OneMore runs in a special location that makes direct communication risky.

 

Why This Design Exists

 

Where OneMore Runs

OneMore runs inside a separate process. It does not run inside OneNote itself. This separate location causes two problems:

 

Problem 1: Calls often fail

Commands travel across a process boundary. The connection is weak. OneNote might be busy. The connection might drop. A simple command is risky.

Solution: Retry every call. If it fails, try again.

 

Problem 2: Objects are not released quickly

.NET normally waits for "garbage collection" to release OneNote objects. This is too slow. While waiting, OneNote gets stuck.

Solution: Release objects immediately after use. Do not wait for garbage collection.

 

How the Layer Works

 

Three Components Work Together

 

1. ApplicationFactory (Activation)

Job: Create the OneNote connection.

  • Creates a new OneNote connection when needed
  • Retries 3 times if activation fails
  • Acts as a helper for tests to use fake connections

Code location: OneMore/Helpers/ApplicationFactory.cs

 

2. OneNote Wrapper (Commands)

Job: Send commands safely.

  • Holds the OneNote connection
  • Adds retry logic around every call
  • Converts raw XML data into usable objects
  • Releases the connection when done

Code location: OneMore/OneNote.cs

 

3. Commands (Usage)

Job: Use the OneNote connection for a short time.

Each command:

  • Creates its own OneNote connection when it starts
  • Uses it to do work
  • Releases it when finished

 

Example:

 

await using (one = new OneNote())

{

var section = await one.GetSection();

var ns = one.GetNamespace(section);

// Use the objects here

}

// OneNote connection is released automatically

When to Retry (and When Not To)

The system checks the error code. Some errors are worth retrying. Some are not.

Retry. Create new objects.

 

How Recovery Works

When a retry is needed:

  1. Release the old broken connection
  2. Create a new connection
  3. Wait (250ms minimum for connection problems)
  4. Try the command again

 

Code example:

 

private void ReplaceApplication()

{

// Release the old connection

if (onenote is not null)

{

try

{

if (Marshal.IsComObject(onenote))

Marshal.FinalReleaseComObject(onenote);

}

catch (Exception exc)

{

logger.WriteLine("error releasing onenote", exc);

}

}

// Create a new connection

onenote = ApplicationFactory.CreateApplication();

}

Object Lifecycle Management

 

Release Objects Immediately

The system does not wait for garbage collection. It releases objects right after use.

Special care: The system releases not just the main connection, but also temporary objects.

Example - Releasing temporary objects:

 

private T WithCurrentWindow<T>(Func<Window, T> reader, T fallback)

{

if (onenote is null) return fallback;

Windows windows;

try

{

windows = onenote.Windows; // Get the Windows collection

}

catch (COMException exc)

{

logger.WriteLine("Cannot get Windows collection", exc);

return fallback;

}

try

{

var window = windows.CurrentWindow; // Get the current window

try

{

return window is null ? fallback : reader(window);

}

catch (COMException exc)

{

logger.WriteLine("Cannot get Window property", exc);

return fallback;

}

finally

{

// Release the window object right away

if (window is not null && Marshal.IsComObject(window))

Marshal.ReleaseComObject(window);

}

}

finally

{

// Release the windows collection right away

if (Marshal.IsComObject(windows))

Marshal.ReleaseComObject(windows);

}

}

 

Key Rules for Object Release

  1. Release immediately. Do not wait for garbage collection.
  2. Use finally blocks. This ensures release even if errors occur.
  3. Check before release. Use Marshal.IsComObject() to verify the object exists.
  4. Use FinalReleaseComObject for broken objects. For objects in a bad state, force release immediately with FinalReleaseComObject.

 

How Concurrent Commands Work

 

No Shared Connection

The system does not use locks or shared connections. Each command gets its own separate connection.

Design principle: If two commands run at the same time, they use separate connections. If they collide, the retry system handles the failure.

Different from UI marshaling: The system SingleThreaded exists for UI work (clipboard, file dialogs). OneNote commands do NOT use SingleThreaded. They rely on retries instead.

 

Recent Improvements (Issue #2455)

 

The system learned from real failures. These changes made it stronger:

 

Change 1: More Errors Trigger Retry at Activation

Before: Only hrCOMBusy triggered retry.

After: Also retry on:

  • hrRpcSysCallFailed
  • hrRpcFailed
  • hrRpcFailed2
  • hrRpcUnavailable

Why: These RPC errors can happen during activation, just like during normal calls.

 

Change 2: Added Error Codes

Added:

  • hrRpcSysCallFailed = 0x80010100 ("RPC system call failed")

Why: Better error identification and logging.

 

Change 3: Protected Window Access

Before: Called onenote.Windows with no protection.

After:

  • Null-check onenote first
  • Wrap in try/catch
  • Return fallback on error instead of crashing

Why: Treat COM failure as normal at every boundary, not just known problem spots.
